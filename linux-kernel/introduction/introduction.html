Many people will say, "I studied pwn in Userland all the way, but it seems difficult from the kernel and I can't help it." However, in fact, with kernel exploit, it is very easy to attack in some cases.
This section explains the differences between userland exploitation and kernel exploitation, environment construction, etc.

Kernel exploit features

First of all, let's understand the characteristics of vulnerabilities in kernel space compared to userland.

Attack target

The biggest difference between userland exploit and kernel exploit is in its purpose.
In the userland exploit described above, we wrote exploit for the goal of "arbitrary command execution" in many cases.On the other hand, the kernel exploit generally writes exploit for "elevation of authority".Assuming that the target machine could be compromised in some way, the attacker would use the kernel exploit to gain further root privileges[1]. Thus, privilege escalation on the local machineLPE(Local Privilege Escalation).
Of course, there are vulnerabilities that allow privilege escalation in userland, but this is because the program being attacked is running as a privileged user. In the case of kernel exploitation, there are two main targets for attack:

  1. Linux Kernel
  2. kernel module

Because the code in the Linux kernel (system calls and file systems) runs with root privileges, a bug in the kernel itself can lead to LPE.
The other is a vulnerability contained in kernel modules such as device drivers.Device drivers are interfaces that facilitate interaction from user space, primarily with external devices (such as printers).The device driver is also always running with root privileges[2]So, if there is a bug, it will lead to LPE.

How to attack

In the case of userland exploitation, the exploit is usually done by providing input to the service being attacked. Therefore, it is common practice to write exploits in languages ​​such as Python.
On the other hand, in the case of kernel exploit, the target is the OS and drivers.Since these operations are low-layer, it is mainstream to write exploit in C language and so on.Of course, you can also write in Python, but since Python rarely exists on the target machine (especially on small Linux such as CTF and experimental environment), it is likely to not work.

This site also describes exploits in C language. The detailed story will appear in another section, butmusl-gccWe will use a compiler called.

Resource Sharing

Another feature of kernel exploit is that resources are shared.
In userland, there is usually one process to attack, and by exploiting that process, attacks can be made such as taking a shell. On the other hand, programs such as the Linux kernel and device drivers are shared by all processes using the OS. Anyone can use system calls at any time, and device drivers do not know who will use them and when. In other words, when writing code that runs in kernel space, you can easily introduce vulnerabilities unless you always plan for multithreading.

This means that when using data that may conflict, such as global variables, you must acquire a lock.
Programming in kernel space is difficult.

Shared heap space

In addition, there is a major feature that the heap area of the kernel is shared by all drivers and the kernel.
Until now, in userland exploit, there was a heap for each program, so it was program-dependent whether it was exploitable because Heap Overflow occurred in that program.However, a single heap overflow on a device driver, for example, can contaminate the surrounding data that other device drivers or the Linux kernel have secured to the heap.

From the attacker's point of view, this feature has advantages and disadvantages. The advantage is that even small vulnerabilities around the heap are very likely to lead to LPE. For example, there are many objects with function pointers in the Linux kernel, so rip can be easily retrieved using one of them. The disadvantage is that the state of the heap cannot be predicted because it is affected by all programs. If the userland program was simple, complex heap exploits (commonly known as House of XXX) were possible because the state of the heap was decisive for the input. On the other hand, the kernel does not know what data is behind the chunk where the Heap Overflow occurs or who will use that address after it is free with Use-after-Free.

So Heap Spray is important in kernel exploit.

The vulnerability itself is not much different from that of the user land. Stack Overflow and Use-after-Free can also exist in the kernel land. You can also place a stack canary on the device driver stack as a security mechanism. However, since there is also a vulnerability specific to kernel space, it will appear in a later section.

Using qemu

When writing a Linux kernel exploit, run the kernel on the emulator for debugging. Any VM is fine, but qemu is common, so we will use qemu on this site as well.

If you are a reader, please install qemu-system according to your environment.

disk image

when you start the machine with qemu, you need a disk image that will be mounted as the root directory separately from the Linux kernel.
Disk images are generally created and distributed as raw binaries of file systems such as ext or in a format called cpio.
If it is a file system, you can edit the files inside by mounting it with the mount command.
