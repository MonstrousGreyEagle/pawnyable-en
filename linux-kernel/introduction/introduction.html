Many people will say, "I studied pwn in Userland all the way, but it seems difficult from the kernel and I can't help it." However, in fact, with kernel exploit, it is very easy to attack in some cases.
This section explains the differences between userland exploitation and kernel exploitation, environment construction, etc.

Kernel exploit features

First of all, let's understand the characteristics of vulnerabilities in kernel space compared to userland.

Attack target

The biggest difference between userland and kernel exploits is their purpose.
In the userland exploits discussed above, we often wrote exploits to achieve “arbitrary command execution.” Kernel exploits, on the other hand, are generally written to achieve “privilege escalation.” Assuming that the target machine has already been compromised by some means, an attacker can use a kernel exploit to obtain further privileges, such as root privileges[1]. Privilege escalation on the local machine is called LPE (Local Privilege Escalation).
Of course, userland vulnerabilities can also allow privilege escalation, but in those cases the attacked program is running as a privileged user. For kernel exploitation, there are two main targets:

  1. Linux Kernel
  2. kernel module

Code in the Linux kernel, such as system calls and file systems, runs with root privileges, so a bug in the kernel itself can lead to LPE.
The other target is vulnerabilities in kernel modules such as device drivers. Device drivers are interfaces that make it easier for user space to communicate with external devices, such as printers. Device drivers also run with root privileges[2], so a bug in one can lead to LPE.

How to attack

For userland exploitation, the exploit usually provides input to the service being attacked. It is therefore common to write exploits in a language such as Python.
For kernel exploitation, the targets are the operating system and its drivers. Because these operations take place at a low level, exploits are commonly written in C. Python can be used as well, but it is unlikely to work because Python is rarely installed on the target machine—especially on the small Linux environments provided for CTFs and experiments.

Exploits on this site are also written in C. The details will be covered in another section, but we will use a compiler called musl-gcc.

Resource Sharing

Another feature of kernel exploits is that resources are shared.
In userland, there is usually one process to attack, and exploiting that process can allow an attacker to obtain a shell. In contrast, programs such as the Linux kernel and device drivers are shared by every process using the operating system. Anyone can invoke system calls at any time, and a device driver does not know who will use it or when. In other words, when writing code that runs in kernel space, you can easily introduce vulnerabilities unless you always design for concurrent execution.

This means that when using data that may conflict, such as global variables, you must acquire a lock.
Programming in kernel space is difficult.

Shared heap space

Another major feature is that the kernel heap is shared by all drivers and by the kernel itself.
In userland exploitation, each program has its own heap, so whether a heap overflow is exploitable depends on that program. In the kernel, however, a single heap overflow in a device driver, for example, can corrupt data belonging to other device drivers or to the Linux kernel.

From the attacker's point of view, this feature has advantages and disadvantages. The advantage is that even small vulnerabilities around the heap are very likely to lead to LPE. For example, there are many objects with function pointers in the Linux kernel, so rip can be easily retrieved using one of them. The disadvantage is that the state of the heap cannot be predicted because it is affected by all programs. If the userland program was simple, complex heap exploits (commonly known as House of XXX) were possible because the state of the heap was decisive for the input. On the other hand, the kernel does not know what data is behind the chunk where the Heap Overflow occurs or who will use that address after it is free with Use-after-Free.

So Heap Spray is important in kernel exploit.

The vulnerabilities themselves are not very different from those found in userland. Stack overflows and use-after-free bugs can also exist in kernel space, and a stack canary can be placed on a device driver’s stack as a security mechanism. However, kernel space also has vulnerabilities specific to it; those will appear in later sections.

Using qemu

When writing a Linux kernel exploit, run the kernel on the emulator for debugging. Any VM is fine, but qemu is common, so we will use qemu on this site as well.

If you are a reader, please install qemu-system according to your environment.

disk image

When you start a machine with qemu, you need a disk image that is mounted as the root directory separately from the Linux kernel.
Disk images are generally created and distributed either as raw file-system images, such as ext, or in a format called cpio.
If the image is a file system, you can edit the files inside it by mounting it with the mount command.
