The Linux kernel has several security mechanisms that mitigate kernel exploits. Some of this knowledge also applies directly to Windows kernel exploits because hardware-level protections, such as NX, are common to both.

What we're talking about here are kernel-specific protections; security mechanisms like Stack Canary also exist in device drivers, but they're not worth mentioning, so we won't discuss them here.

For information about kernel boot parameters, the official documentation is helpful.

SMEP (Supervisor Mode Execution Prevention)

Representative kernel security mechanisms are SMEP and SMAP.
SMEP is a security mechanism that prevents user space code from suddenly running while kernel space code is running. The image is similar to NX.

SMEP is a hardware security mechanism. It is enabled by setting bit 21 of the CR4 register.

SMAP (Supervisor Mode Access Prevention)

It is natural that user space cannot read or write kernel-space memory for security reasons. However, there is also a mechanism called SMAP (Supervisor Mode Access Prevention), which prevents kernel space from reading or writing user-space memory. To access user-space data from kernel space, you must use functions such as copy_from_user and copy_to_user.

KASLR / FGKASLR

User space has ASLR (Address Space Layout Randomization), which randomizes addresses. Similarly, KASLR (Kernel ASLR) randomizes the addresses of code and data in the Linux kernel and device drivers.
The kernel does not move after it is loaded, so KASLR operates only once at startup. If you can leak the address of any kernel function or data, you can determine the kernel’s base address.

Since 2020, an even stronger form of KASLR called FGKASLR (Function Granular KASLR) has been available. It randomizes the address of each function in the Linux kernel, although it appears to be disabled by default as of 2022. Leaking a kernel function address therefore does not reveal the base address.
FGKASLR does not randomize data sections, however, so leaking a data address still reveals the base address. Although a specific function address cannot then be derived from the base address, this can still be useful for special attack vectors discussed later.

Note that addresses are common in kernel space. Even if one device driver is unable to exploit due to KASLR, if another driver leaks the kernel's address, the address will be exploitable because it is common.

KASLR can be disabled with a kernel boot argument. It is disabled when the qemu -append option includes nokaslr.

KPTI (Kernel Page-Table Isolation)

In 2018, a side-channel attack called Meltdown was discovered in Intel and other CPUs. We will not explain the vulnerability here, but it allowed kernel-space memory to be read with user privileges and made it possible to bypass KASLR. As a mitigation against Meltdown, recent Linux kernels enable KPTI (Kernel Page-Table Isolation), formerly called KAISER.

Page tables are used to translate virtual addresses to physical addresses. This security mechanism separates the page tables used in user mode and kernel mode[2]. KPTI prevents Meltdown, so it is not normally a problem for kernel exploits. However, when KPTI is enabled, operations such as kernel-space ROP can cause problems when returning to user space. Specific solutions will be covered again in the Kernel ROP chapter.

KPTI can be controlled with kernel boot arguments. It is enabled when the qemu -append option includes pti=on, and disabled when it includes pti=off or nopti.

You can also check KPTI at /sys/devices/system/cpu/vulnerabilities/meltdown. If the output contains “Mitigation: PTI,” KPTI is enabled.

If it is invalid, it will be "Vulnerable".

Since KPTI is a page table switch, you can switch the user kernel space by operating the CR3 register. On Linux, you switch from kernel space to user space by ORing 0x1000 to CR3 (i.e., changing the PDBR). KADR (Kernel Address Display Restriction)

In Linux, you can read kernel symbol names and addresses from /proc/kallsyms. Some device drivers also use functions such as printk to output debugging information to the log, which users can view with commands such as dmesg.
Linux therefore has mechanisms to prevent kernel-space function, data, and heap addresses from leaking. These mechanisms do not appear to have an official name. A reference calls them KADR (Kernel Address Display Restriction), so we use that name here as well.

You can change this feature through /proc/sys/kernel/kptr_restrict. If kptr_restrict is 0, kernel addresses are displayed without restriction. If it is 1, users with CAP_SYSLOG can see the addresses. If it is 2, kernel addresses are hidden even from privileged users.
If KADR is disabled, an address leak is unnecessary, so exploitation may be easier; check this setting first.

Download the LK01 practice files and, from the root shell obtained in the previous exercise, do the following:
(1) Run run.sh and check whether KASLR, KPTI, SMAP, and SMEP are enabled.
(2) Start qemu with both SMAP and SMEP enabled, then check /proc/cpuinfo to confirm that they are active. (Disable SMAP and SMEP again after checking.)
(3) Run head /proc/kallsyms. The first address shown is the kernel base address. If KASLR is disabled, check what the base address is. (Hint: beware of KADR.)
