Several security mechanisms exist in the Linux kernel to mitigate against kernel exploits. Some of the knowledge can be directly applied to Windows kernel exploits, as there are security mechanisms at the hardware level, such as NX, which appeared in userland.

What we're talking about here are kernel-specific protections; security mechanisms like Stack Canary also exist in device drivers, but they're not worth mentioning, so we won't discuss them here.

SMEP (Supervisor Mode Execution Prevention)

Representative kernel security mechanisms are SMEP and SMAP.
SMEP is a security mechanism that prevents user space code from suddenly running while kernel space code is running. The image is similar to NX.

KASLR / FGKASLR

In the user space, there was an ASLR (Address Space Layout Randomization) that randomized addresses. Similarly, randomize the address of the code data area of the Linux kernel or device driverKASLRThere is also a mitigation mechanism called (Kernel ASLR).
The kernel does not move once it is loaded, so KASLR only works once at startup.If you can leak the address of any one of the functions or data in the Linux kernel, you will find the base address.

Since entering 2020,FGKASLR(Function Granular KASLR), which seems to be disabled by default as of 2022, is a technique that randomizes addresses for each function in the Linux kernel. Even if the address of the function in the Linux kernel can be leaked, the base address is not found.
However, FGKASLR does not randomize data sections, etc., so if the address of the data can be leaked, the base address will be obtained.Although it is not possible to obtain the address of a specific function from the base address, it is available for special attack vectors that will appear later.

Note that addresses are common in kernel space. Even if one device driver is unable to exploit due to KASLR, if another driver leaks the kernel's address, the address will be exploitable because it is common.

KPTI (Kernel Page-Table Isolation)

Intel and other CPUs in 2018MeltdownA side-channel attack called has been detected. Although this vulnerability is not explained, it is a serious vulnerability that allows the memory in the kernel space to be read with user privileges, and it was possible to avoid KASLR. In recent years, as a measure of Meltdown in the Linux kernel,KPTI(Kernel Page-Table Isolation), or the old nameKAISERmechanism is enabled.

As you know, page tables are used when converting virtual addresses to physical addresses, but separating this page table in user mode and kernel mode[2]is this security mechanism. KPTI is a security mechanism to prevent Meltdown, so it is not a problem in normal kernel exploit. However, when KPTIs are enabled, such as when ROPing in kernel space, problems arise when finally returning to user space. Specific solutions will be revisited in the Kernel ROP chapter.

KPTI can be enabled with kernel boot arguments. qemu -append to options pti=on KPTIs are enabled if pti=off PNG and .nopti If it is, it will be deactivated.

KPTIs are /sys/devices/system/cpu/vulnerabilities/meltdown You can also check it out here. If "Mitigation: PTI" is written as follows, KPTI is valid.

If it is invalid, it will be "Vulnerable".

Since KPTI is a page table switch, you can switch the user kernel space by operating the CR3 register. On Linux, you switch from kernel space to user space by ORing 0x1000 to CR3 (i.e., changing the PDBR). In the Linux kernel, the name and address information /proc/kallsyms You can read it at. Also, depending on the device driver,printk Some use functions, etc., to output various debugging information to the log, and this log is dmesg It can be viewed from the user with commands and so on.
In this way, Linux has a mechanism to prevent the leakage of address information such as kernel space functions, data, and heaps.I don't think it has an official name.Referencesentry in toKADRIt seems to be called (Kernel Address Display Restriction), so we will adopt that name on this site as well.

This feature is only available in /proc/sys/kernel/kptr_restrict You can change it by the value of.kptr_restrict If is 0, there is no restriction on the display of the address.kptr_restrict If is 1,CAP_SYSLOG Users with permissions will see the address.kptr_restrict If is 2, the kernel address is hidden even if the user is at the privilege level.
If KADR is disabled, there is no need for an address leak, so it may be easier to exploit if you check it first.
