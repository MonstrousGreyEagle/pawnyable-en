Introduction

After studying kernel exploitation for about two months, I have found kernel UAFs and heap overflows to be extremely powerful. Exploitation often relies not only on the vulnerable driver's interface, but also on features provided by the kernel and other drivers. Without that background, attacks become harder to develop and less reliable.

For example, a kernel UAF is very useful, but when the freed object has a fixed size, you must find an object of the same kmalloc size that is also useful to an attacker. This page collects such objects. The experiments used Linux 4.19.98; object sizes and behavior may differ on other kernel versions.

Structures useful for leaks, AAR/AAW, and RIP control

The following list is organized by allocation size. “Base” means a kernel-text or module pointer, “heap” a heap pointer, and “stack” a stack pointer.

shm_file_data

  • Size: 0x20 (kmalloc-32).
  • Leaks: vm_ops points into kernel data and file can point into the heap.
  • Allocate: map shared memory with shmat. Release it with shmctl.
  • RIP control was not observed by replacing vm_ops.

seq_operations

  • Size: 0x20 (kmalloc-32).
  • Its four function pointers can leak the kernel base.
  • Allocate by opening a file using single_open, such as /proc/self/stat; release with close.
  • Replacing start and calling read can control RIP.

msg_msg plus user data

  • Size: 0x31–0x1000 (kmalloc-64 and larger).
  • next points to another message, making it useful for heap leaks.
  • Allocate with msgget and msgsnd; release with msgrcv.
  • The first 48 bytes are occupied by the message header, but the remaining user-controlled data makes this useful for spraying.

subprocess_info

  • Size: 0x60 (kmalloc-128).
  • work.func points to call_usermodehelper_exec_work, providing a kernel-base leak.
  • Allocate, for example, by requesting an unknown protocol with socket(22, AF_INET, 0).
  • A race while cleanup is being used may provide RIP control.

cred

  • Size: 0xa8 (kmalloc-192).
  • Members such as session_keyring may leak a heap address.
  • Fork to allocate and exit the child to release it.
  • It contains UID and GID fields, but on the tested 4.19.98 kernel it did not appear to be allocated from ordinary kmalloc.

file

  • Size: approximately kmalloc-256.
  • f_op points into kernel data and can leak the base.
  • Create a shared-memory object with shmget and release it with shmctl.
  • Replacing f_op may provide RIP control, although overlap was not reproduced in the original test.

timerfd_ctx

  • Size: approximately kmalloc-256.
  • tmr.function points to timerfd_tmrproc; tmr.base can expose a heap pointer.
  • Allocate with timerfd_create and release by closing the descriptor.

tty_struct

  • Size: 0x2e0 (kmalloc-1024).
  • ops points to ptm_unix98_ops; dev and driver also expose heap relationships.
  • Open /dev/ptmx to allocate and close it to release.
  • Replacing ops can control RIP.

Structures for arbitrary data and heap sprays

msg_msg

See the section above. Its variable-sized user data makes it a general-purpose heap spray.

setxattr

  • Size: arbitrary, up to 65536 bytes.
  • Call setxattr, passing the data pointer as value and its length as size.
  • The allocation is released on the same path. Combined with userfaultfd, it can write headers that msgsnd cannot control.

sendmsg

  • Size: arbitrary, at least 2 bytes.
  • Put the buffer pointer in msg.msg_control and its size in msg.msg_controllen.
  • Like setxattr, it is useful with userfaultfd for controlled heap spraying.
